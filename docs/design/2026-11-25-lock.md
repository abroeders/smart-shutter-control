# Lock or force shutters from an automation

- Issue: #52
- Status: **approved** (2026-11-25)
- Date: 2026-11-25

## 1. Purpose

Automations need to put some or all shutters in a fixed state for a while: closed on a hail warning, open while
the windows are washed, or "leave everything where it is". Today an automation can only turn *Automatic
control* off and move the cover itself, which loses storm, frost and the door safety.

## 2. What the user sees

- An action **`smart_shutter_control.set_lock`** with:
  - **target**: one or more shutter devices of the integration;
  - **mode**: `none` (end the lock), `hold` (the controller does not move the shutter), `force_open` (fully
    open, 100 %), `force_closed` (fully closed, 0 %);
  - **duration** (optional): how long the lock lasts; without it the lock lasts until it is ended.
- A **select** entity per shutter, *Lock* (Dutch *Vergrendeling*), with the same four options; it shows the
  current lock and sets one without a duration. Attribute `until` (the end time, or none).
- Reason **`locked`** in the *Reason* sensor and the card, with the mode in the decision trace.

## 3. Behaviour

### Order of the rules

| Priority | Rule | With a lock |
|---|---|---|
| 10 | storm | wins: the storm position, as now |
| 11 | frost | wins: no moves |
| **12** | **lock** | final decision for everything below |
| 15 … 60 | temperature limits, manual pause, sleep-in, heat, glare, winter, schedule | not used |

The open-door and tilted-window floors (#49) are applied after the rule chain, as now, so a `force_closed`
shutter is still raised to its lockout or ventilation position while the door or window is open.

### The modes

| Mode | Decision |
|---|---|
| `hold` | no target: the controller does not move the shutter (like frost) |
| `force_open` | 100 %, also above the *Maximum position* (an explicit order, like manual operation) |
| `force_closed` | 0 % |
| `none` | no lock |

### When a lock ends

- Its duration has passed.
- `set_lock` with `none`, or the select set to *None*.
- **Any manual action** on that shutter (wall switch, remote, app, the integration's own cover or position
  entity): the lock ends and the usual manual handling follows (the manual pause, per the manual mode).
- The button *Resume automatic control*: it ends the lock as well as the manual pause.

When a lock ends, the next evaluation moves the shutter to what automatic control wants (`last_target` is
cleared, as when a manual pause ends).

### Other situations

- *Automatic control* off for the shutter, or the whole integration paused (#53): nothing moves; the lock is
  kept and applies again when control is back on (unless it has expired meanwhile).
- A restart keeps the lock and its end time (runtime store, key `lock`); an expired lock is dropped at start.
- A new `set_lock` on a locked shutter replaces the lock (mode and end time).
- The calibration assistant pauses the controller as now; the lock applies again when it is done.

## 4. Design

- `core/lock.py` (pure Python):
  - `LockMode` (StrEnum: `none`, `hold`, `force_open`, `force_closed`).
  - `Lock` (dataclass: `mode`, `until: float | None`; `on`, `still(now)` drops an expired lock, `to_dict` /
    `from_dict`) — the same shape as `ManualPause` (Repository via the runtime store).
  - `LockRule` (priority 12, `Decision(..., Reason.LOCKED, final=True)`; `why` for the decision trace).
- `core/model.py`: `Reason.LOCKED = "locked"`.
- `core/rule_factory.py`: `LockRule` in the chain of every shutter.
- `controller.py`: `lock` loaded from and saved to the store; `set_lock(mode, duration)`; `_manual()` and
  `resume()` end the lock; `lock` in the diagnostics.
- `__init__.py`: the action is registered in `async_setup` (not per entry, as Home Assistant asks), with a
  schema (`mode` required, `duration` optional time period); devices are resolved to controllers through the
  subentry device identifiers; an unknown device raises `ServiceValidationError`.
- `services.yaml` with a device target filtered on the integration, `mode` as a select, `duration` as a
  duration selector; translations of the action and its fields (en, nl).
- `select.py`: `LockSelect` per shutter (translation key `lock`, options translated).
- Card (`frontend/src/localize.ts` en + nl): reason `locked` and the rule name `lock`.
- `docs/architecture.md`: class diagram (`Lock`, `LockRule`), the rule order table, a sequence diagram of
  `set_lock` and a state diagram (unlocked → locked → ended by time / action / manual / resume).
- User docs: `entities.md` (select), `how-it-works.md` (locks and their order), a new section *Actions* with
  examples (hail warning, washing windows), FAQ.

## 5. Tests

- `tests/test_lock.py`: each mode's decision; storm and frost win; the lock wins over heat, glare and the
  schedule; expiry; `to_dict`/`from_dict`; an expired lock is dropped.
- `tests_ha/test_lock.py`: the action on one and on two devices, with and without duration; an unknown device;
  the select shows and sets the lock; a manual move ends it; *Resume* ends it; a restart keeps it; the open-door
  floor still raises a `force_closed` shutter; reason `locked` in the sensor.

## 6. Out of scope

- Rain or hail sensors as a built-in trigger (an automation calls the action).
- A lock for the whole integration in one entity (the action can target all shutter devices).
- Other modes (a free position, the slit).
